Format support

Lumen identifies a file by its bytes, not its extension. A .mkv renamed to .mp4, or a signed URL with no extension at all, still routes correctly.

Containers vs codecs

Playing a video needs two things: a container the player can parse, and codecs the browser can decode. They fail independently.

Containers are just packaging, so Lumen rebuilds them in JavaScript. Codecs are a hard limit — no player can decode what the browser can't without shipping a multi-megabyte WASM decoder, which would cost more than the rest of the player combined.

Duration while streaming

A MediaSource reports no duration until something sets one, so a remuxed file used to show 0:00 / 0:00 until the whole thing had downloaded. Lumen reads the length out of the container's header — Matroska's Segment info, or the AVI stream header — and publishes it immediately, so the scrub bar works from the first second. End-of-stream then corrects it to what the file actually held, which matters for a truncated upload whose header still describes the original.

How codec failures degrade

SourceResult
H.264, HEVC, VP9, AV1 videoRemuxed and played

AC-3, DTS, TrueHD, PCM audioAudio dropped, video still plays, viewer told why
MPEG-4 ASP (DivX/Xvid), MJPEG, WMVNamed in the error, so the container doesn't take the blame
Undecodable video codecClear message naming the fix
That AC-3 case matters more than it sounds: it's the single most common reason an MKV "won't play", and dropping one track beats refusing the file.

Handling the unplayable

player.on("error", ({ code, message }) => {
  if (code === "CONTAINER_UNSUPPORTED") {
    // e.g. "This AVI's video is MPEG-4 ASP (XVID), which no browser
    //       can decode. Converting it to H.264 MP4 will fix it."
    offerServerSideTranscode(message);
  }
});

Why AVI is a codec problem, not a container problem

AVI is the format the web is usually told to give up on. The container itself is trivial — a flat list of length-prefixed chunks with the stream headers at the front — and Lumen parses it while it downloads. What is genuinely impossible is decoding what most AVIs carry: MPEG-4 ASP, which ships in no browser.

Conflating those two is why "AVI doesn't work" became folklore. An AVI holding H.264 and MP3 or AAC — which every modern re-encode and every camera-to-AVI tool produces — is a container rewrite away from playing, and that is what Lumen does. An AVI holding Xvid gets an error that names Xvid.

Known limits

  • Seeking a remuxed MKV uses the file's Cues index. Files muxed without one fall back to seeking within buffered ranges.
  • AVI covers H.264 video with MP3 or AAC audio; the container is parsed either way, but MPEG-4 ASP has no browser decoder. AVI seeking is limited to buffered ranges — the idx1 index at the end of the file isn't used yet.
  • WMV/ASF and MPEG program streams are detected but not demuxed — their codecs are undecodable in browsers anyway.
  • VP9-in-MKV synthesizes its vpcC with profile-0 / 8-bit / 4:2:0 defaults, since Matroska usually stores none.
  • Bitmap subtitles (VOBSUB, PGS) in MKV are skipped; only text-based tracks become text tracks.
