Format support

Lumen identifies a file by its bytes, not its extension. A .mkv renamed to .mp4, or a signed URL with no extension at all, still routes correctly.

Containers vs codecs

Playing a video needs two things: a container the player can parse, and codecs the browser can decode. They fail independently.

Containers are just packaging, so Lumen rebuilds them in JavaScript. Codecs are a hard limit — no player can decode what the browser can't without shipping a multi-megabyte WASM decoder, which would cost more than the rest of the player combined.

How codec failures degrade

SourceResult
H.264, HEVC, VP9, AV1 videoRemuxed and played
AAC, Opus, FLAC, MP3 audioRemuxed and played
AC-3, DTS, TrueHD audioAudio dropped, video still plays, viewer told why
Undecodable video codecClear message naming the fix
That AC-3 case matters more than it sounds: it's the single most common reason an MKV "won't play", and dropping one track beats refusing the file.

Handling the unplayable

player.on("error", ({ code, message }) => {
  if (code === "CONTAINER_UNSUPPORTED") {
    // e.g. "AVI files can't be played in a browser.
    //       Converting this to MP4 or WebM will fix it."
    offerServerSideTranscode(message);
  }
});

Known limits

  • Seeking a remuxed MKV uses the file's Cues index. Files muxed without one fall back to seeking within buffered ranges.
  • AVI/WMV/FLV-with-VP6 are detected but not demuxed — their codecs are mostly undecodable in browsers anyway.
  • VP9-in-MKV synthesizes its vpcC with profile-0 / 8-bit / 4:2:0 defaults, since Matroska usually stores none.
  • Bitmap subtitles (VOBSUB, PGS) in MKV are skipped; only text-based tracks become text tracks.
